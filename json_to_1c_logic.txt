# Логика преобразования JSON в формат 1С 7.7 и анализ типов

## 1. Алгоритм преобразования

Основная идея - создать корневой `СписокЗначений`, который будет содержать другие `СпискиЗначений`, где каждый вложенный список представляет одну транзакцию из JSON-файла.

1.  **Загрузка и парсинг:** Прочитать и разобрать (parse) файл `prinvat.json` как стандартный JSON.

2.  **Создание корневого элемента:** Создать главный `СписокЗначений` (назовем его `СЗ_Выписка`). Этот список будет хранить все транзакции.

3.  **Итерация по транзакциям:** Получить доступ к массиву по ключу `transactions`. Пройти в цикле по каждому элементу этого массива (каждый элемент - это JSON-объект, представляющий одну транзакцию).

4.  **Обработка одной транзакции:** Для каждого `объекта_транзакции` в цикле:
    a. Создать новый `СписокЗначений` для этой транзакции (например, `СЗ_Транзакция`).
    b. Перебрать все пары `ключ:значение` внутри `объекта_транзакции`.
    c. Для каждой пары, в зависимости от типа и содержимого `значения`, определить соответствующий тип для 1С и отформатировать его согласно правилам:
        *   **`null`:** Если значение `null`, оно преобразуется в пустую строку `""`. Тип для 1С - `Строка` (код `S`).
        *   **`boolean`:** Если значение `true` -> `1`, `false` -> `0`. Тип для 1С - `Число` (код `N`).
        *   **`строка` (string):**
            1.  Проверить, соответствует ли строка формату даты `ДД.ММ.ГГГГ`. Если да, преобразовать ее в формат `ГГГГММДД` и назначить тип `Дата` (код `D`).
            2.  Если не дата, проверить, является ли строка числом (например, "150.00"). Если да, оставить как есть и назначить тип `Число` (код `N`).
            3.  Во всех остальных случаях считать значение обычной строкой. Перед записью необходимо экранировать двойные кавычки (`"` заменяется на `""`). Тип - `Строка` (код `S`).
        *   **`число` (number):** Если в JSON есть числовой тип, преобразовать его в строковое представление и назначить тип `Число` (код `N`).
    d. Добавить полученное отформатированное значение и его ключ в `СЗ_Транзакция`.
    e. Добавить `СЗ_Транзакция` в корневой `СЗ_Выписка`. В качестве ключа для этой записи рекомендуется использовать уникальный идентификатор транзакции, например, значение поля `TECHNICAL_TRANSACTION_ID`.

5.  **Сериализация:** После обработки всех транзакций, сериализовать итоговый `СЗ_Выписка` в текстовую строку согласно формату, описанному в `conversion_rules.txt`.

## 2. Анализ типов и что еще стоит учесть

### Анализ типов в `prinvat.json`

При сопоставлении с правилами для 1С выявляются следующие особенности:

1.  **Числа в виде строк:** Поля, обозначающие суммы (`SUM`, `SUM_E`), представлены как строки (`"150.00"`), а не как числовые литералы JSON (`150.00`). Алгоритм должен уметь распознавать такие строки и корректно назначать им тип `Число` (`N`).

2.  **Даты:** Даты (`DAT_KL`, `DAT_OD`) представлены в строковом формате `ДД.ММ.ГГГГ`. Для преобразования в формат 1С (`D`) их необходимо переформатировать в `ГГГГММДД`.

3.  **Дата и время:** В JSON есть комбинированное поле `DATE_TIME_DAT_OD_TIM_P` ("01.01.2026 09:00:00") и отдельное поле времени `TIM_P` ("09:00").
    *   **Рекомендация:** Поскольку в 1С 7.7 нет отдельного типа для времени или даты-времени, наиболее правильным будет:
        *   Поля `DAT_KL` и `DAT_OD` преобразовывать в тип `Дата` (`D`).
        *   Поля `TIM_P` и `DATE_TIME_DAT_OD_TIM_P` преобразовывать в тип `Строка` (`S`), чтобы не терять информацию о времени.

4.  **Логический тип (Boolean):** Поле `exist_next_page` имеет тип `boolean`. В правилах для 1С нет такого типа. Стандартной практикой является его преобразование в число: `false` -> `0`, `true` -> `1`. Тип, соответственно, `Число` (`N`).

5.  **Null:** В данных встречается `null` (например, в поле `DLR`). Это значение не определено в правилах.
    *   **Рекомендация:** Безопаснее всего преобразовывать `null` в пустую строку (`""`) с типом `Строка` (`S`), так как это наиболее универсальный "пустой" тип для 1С.

### Что еще учесть

*   **Кодировка:** JSON-файл использует кодировку UTF-8. При создании конечного файла для 1С 7.7 может потребоваться кодировка `Windows-1251` (или `cp1251`). Этот аспект нужно контролировать при реализации.
*   **Вложенные структуры:** В текущем JSON все транзакции плоские (нет вложенных JSON-объектов). Если бы они появились, их можно было бы рекурсивно преобразовать во вложенные `СпискиЗначений` по аналогии с полем "Массив" из файла `1c.txt`.
*   **Отсутствующие поля:** Некоторые транзакции могут не содержать определенных полей (например, `UETR`). Алгоритм должен спокойно это обрабатывать, просто не добавляя отсутствующие поля в `СЗ_Транзакция`.
